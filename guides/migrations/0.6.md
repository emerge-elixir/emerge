# Migrate from Emerge 0.5.x to 0.6.0

The main change is that six mouse event handlers now receive the pointer position.
If your application uses these events, update its message patterns as shown below.
`Event.on_press/1`, other element events, raw input callbacks and viewport
configuration do not need to change.

The 0.6 changes are not yet released. If upgrading from 0.4, follow the
[0.5 migration guide](0.5.md) first.

## 1. Update the dependency

Once 0.6.0 is available, change `mix.exs`:

```elixir
{:emerge, "~> 0.6.0"}
```

Then run `mix deps.update emerge` and restart your application. On supported
targets, Emerge normally downloads matching native components automatically. If
you supply your own native binaries, update them to the same Emerge release,
including the window host on macOS. See [viewport configuration](https://hexdocs.pm/emerge/Emerge.html#module-viewport-configuration)
for source-build and platform settings.

## 2. Update mouse event handlers

These registrations stay the same, but their messages now include a
`%{x: float(), y: float()}` position:

- `Event.on_click/1`
- `Event.on_mouse_down/1` and `Event.on_mouse_up/1`
- `Event.on_mouse_move/1`
- `Event.on_mouse_enter/1` and `Event.on_mouse_leave/1`

With the default payload wrapper, an atom or other non-tuple message becomes
`{message, position}`. For a tuple message, the position is appended:

| Registration | Message in 0.5 | Message in 0.6 |
| --- | --- | --- |
| `Event.on_click(:clicked)` | `:clicked` | `{:clicked, position}` |
| `Event.on_mouse_move({:pointer, :pad})` | `{:pointer, :pad}` | `{:pointer, :pad, position}` |

For example, change the receiving viewport's handlers:

**0.5:**

```elixir
def handle_info(:clicked, state) do
  {:noreply, Map.update!(state, :clicks, &(&1 + 1))}
end

def handle_info({:pointer, :pad}, state) do
  {:noreply, Map.put(state, :pointer, :moved)}
end
```

**0.6:**

```elixir
def handle_info({:clicked, _position}, state) do
  {:noreply, Map.update!(state, :clicks, &(&1 + 1))}
end

def handle_info({:pointer, :pad, %{x: x, y: y}}, state) do
  {:noreply, Map.put(state, :pointer, {x, y})}
end
```

Use `_position` if you do not need the coordinates. The same rules apply when
an event is sent to another process with `{pid, message}`: update the receiving
process's patterns too. Update any tests that send or match these messages.
Old patterns still compile, but may cause a receiver to crash or silently ignore
an event.

`Event.on_press/1` still sends its message unchanged and remains the recommended
choice for ordinary buttons. It also supports keyboard activation, unlike
`on_click/1`, so do not replace a click handler without considering that change.

### If you use a custom payload wrapper

A viewport's `wrap_payload/3` is now called for these six events, with the
position map and an event kind such as `:click` or `:mouse_move`. Update custom
wrappers that assume those events have no payload, and adjust their recipients.

For example, a wrapper that combines a widget ID and position into one map can
handle the new events and delegate everything else to the default wrapper:

```elixir
def wrap_payload({:widget_event, id}, position, kind)
    when kind in [:click, :mouse_down, :mouse_up, :mouse_move, :mouse_enter, :mouse_leave] do
  {:widget_event, %{id: id, position: position}}
end

def wrap_payload(message, payload, kind) do
  Emerge.default_wrap_payload(message, payload, kind)
end
```

If your application intentionally ignores positions, a custom wrapper can
return the original message for these event kinds instead.

### If you use EmergeSkia directly

If you receive element events through `EmergeSkia.set_input_target/2`, update
those patterns too. For example:

```elixir
# 0.5
{:emerge_skia_event, {element_id, :mouse_move}}

# 0.6
{:emerge_skia_event, {element_id, :mouse_move, %{x: x, y: y}}}
```

Raw input observer messages are unchanged.

## 3. Use the position

- Coordinates are floats in logical pixels, measured from the listening element's
  outer top-left corner, including its border and padding.
- Display scaling, element transforms and ancestor scrolling are already accounted
  for. Do not divide the position by the display scale again. For example, at
  scale 2, a point 71 physical pixels from the left edge reports `x: 35.5`.
- Positions are not clamped. A mouse-leave position may be negative or outside
  the element. Leaving the window reports the last known position.
- Mouse down reports the press position; mouse up and click report the release
  position. Mouse up goes to the element under the release, not necessarily the
  element that received the press.

No raw input subscription is needed for these element events. For more examples,
see [Handle input](../tutorials/handle_input.md).

### Optional: drag outside an element

For a custom control such as a color picker, the new `Event.on_drag/1` follows a
left-button drag even when the pointer moves or is released outside the element.
It sends a position map with a `:start`, `:move`, `:end` or `:cancel` phase. This
is optional; existing mouse handlers do not need to use it.

Window leave or focus loss cancels a drag. Removing or hiding the control can
end capture without a final message, so reset any drag state when doing so. Do
not attach `on_drag/1` to native text inputs or sliders, or combine it with
click/press, swipe or virtual-key handlers on the same element. See the
[drag example](../tutorials/handle_input.md#drag-outside-a-custom-control) for a
complete handler.
